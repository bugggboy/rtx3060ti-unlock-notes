# 把 RTX 3060 Ti 的 Tensor Core 从半速解锁到满速：一次完整的实战记录

> 全程 Windows 原生环境，不用 U 盘启动、不装 Linux、不刷 VBIOS、不改 NVIDIA 驱动。
> 最终实现开机自动解锁，无感知。
>
> 硬件：i5-12400F + MSI B660M MORTAR MAX WIFI DDR4 + RTX 3060 Ti 8GB（GA104，`24c910de`）
> 系统：Windows，驱动 610.88，Secure Boot 关闭

---

## 一、先说结论

| 精度路径 | 解锁前 | 解锁后 | 提升 |
|---|---|---|---|
| BF16 + FP32 累加 | 35.97 TFLOPS | **65.45 ~ 67.85** | **+82% ~ +89%** |
| FP16 + FP32 累加 | 35.77 TFLOPS | **66.07** | **+85%** |
| TF32 张量核心 | 17.99 TFLOPS | **33.39** | **+86%** |
| FP32（CUDA 核心） | 13.96 TFLOPS | 13.47 | 不变 |

归一化到「每 SM 每时钟的 FLOP」：

```
解锁前  ~500 FLOP/clk/SM     ← 正好是专业卡的一半
解锁后  ~861 FLOP/clk/SM     ← 专业 GA102 是 1024
```

这个数字才是判断「有没有被限速」的可靠依据，绝对值会随频率、功耗、散热波动。

## 二、这个「半速锁」到底是什么

NVIDIA 在消费级 Ampere（GA102/103/104/106）上限制的不是算力单元，而是**指令发射速率**：

| 运算路径 | 专业卡 | 消费卡（出厂） |
|---|---|---|
| FP16 输入 → **FP16** 累加 | 全速 | 全速 |
| FP16 输入 → **FP32** 累加 | 全速 | **半速** |
| BF16 输入 → **FP32** 累加 | 全速 | **半速** |
| TF32 | 全速 | **半速** |

注意一个关键点：**FP16 累加是全速的**。所以如果你只测 `FP16 + FP16 累加`，会误以为没问题。
现代训练、LoRA、FlashAttention 大量使用 FP32 累加来保证数值稳定性，被卡住的正是这条路径。

控制它的是一组内部寄存器：

| 寄存器 | 偏移 | 含义 |
|---|---|---|
| `SS0` | `0x82381c` | 主速度选择器，出厂 `0x26002014` |
| `SS1` | `0x823820` | 4 位次选择器，出厂 `0x7` |
| `PLM` | `0x823804` | 权限级掩码，出厂 `0xffffff8f` |
| `WPR2_HI` | `0x1fa828` | 写保护，出厂 `0` |

解锁要做的事就两件：把 `SS0` 写成 `0x88888888`、`SS1` 写成 `0x8`，然后让 GPU 重新初始化一次（FLR）。

难点在于 `PLM` 保护：普通驱动写不进这些寄存器。公开的做法（源自 CMP 矿卡解锁研究）是**在 GPU 固件执行的早期窗口里用 ROP 链改掉权限掩码**，这条路必须赶在 NVIDIA 驱动接管显卡之前完成——这就是为什么所有方案都要在预启动环境里跑。

## 三、先判断你的卡有没有锁

不要急着动手，先量化。

用 PyTorch 跑 8192³ 的 GEMM，取中位数：

```python
import torch
a = torch.randn(8192, 8192, dtype=torch.bfloat16, device='cuda')
b = torch.randn(8192, 8192, dtype=torch.bfloat16, device='cuda')
for _ in range(3): c = a @ b
torch.cuda.synchronize()
t = timeit(...)  # 5 次取中位数
tflops = 2 * 8192**3 / t / 1e12
```

然后算归一化值：

```
FLOP/clk/SM = TFLOPS × 1e12 ÷ (SM数 × 频率Hz)
```

- 3060 Ti：38 SM
- 结果 ≈ 500 → **被限速**
- 结果 ≈ 950~1050 → 已经是满速（可能是专业卡，或者已经被解锁过）

实测中还有一个容易误判的地方：**功耗上限会压住成绩**。3060 Ti 有 200W/265W/310W 不同版本，我这张是 265W，跑满时功耗墙先到，频率会在 1900~2000 MHz 之间浮动。所以一定要用归一化值判断，不要看绝对 TFLOPS。

## 四、三条技术路线，为什么选这条

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **Linux 内核模块** | initramfs 里加载 kmod，驱动绑定前改寄存器 | 上游主推，最完整 | 要装 Linux，双系统或整机迁移 |
| **U 盘 EFI** | U 盘启动到 EFI 程序执行解锁 | 不污染系统 | 每次开机都要插 U 盘、手动选启动项 |
| **Windows 内部引导** | 注册独立 ESP 分区 + 固件启动项，在 Windows 自己的启动链里插入解锁 | 一次配置，长期无感 | 需要手工构造启动项，平台适配要自己调 |

我选第三条。前提是你的机器满足：

- **无核显**（或被禁用）——解锁过程会释放显示驱动，屏幕会黑，有第二个显示输出会干扰
- Secure Boot 能关
- 有一块 ≥1GB 的空闲分区可以做成 FAT32 独立 ESP

我这边是 i5-12400F（无核显）+ 一块 2GB 分区，正好。

## 五、完整流程

### 5.1 准备固件资产

解锁需要 5 个文件，来自 NVIDIA 官方 Linux 驱动包 `610.43.03`：

```
booter_load_ga102.bin        61256
v67-ga102-610.43.03.bin      64000
gsp_ga10x.bin             84277400
gsp_boot_ga102.bin           24576
gsp_boot_desc_ga102.bin         84
```

其中 `v67-...bin` 需要用 Python 的 `compression.zstd` 从驱动包里解出来（`zstd` 命令行也能做，但 Windows 上不一定有）。

**必须校验 SHA-256**，程序内置了期望值，对不上会直接拒绝运行。我这边五个哈希全部匹配才继续。

### 5.2 只读采集：搞清楚你的卡长什么样

解锁程序对硬件极度保守：它要求「芯片 ID、子系统 ID、显存大小、BAR0 地址、NVGOP 版本、PROM 哈希、冷状态寄存器」全部匹配才肯动手。

所以先跑一个**纯只读**的探针，把这块卡的真实参数采集出来。探针约束：

- 只读，不写任何寄存器
- 跑在预启动环境
- 输出写到独立分区的文本文件

采集到的关键信息：

```
chip        0xb74000a1
subsystem   16fb10de
memory      0x2000        (8GB)
BAR0        0x80000000
NVGOP       0x60015
PROM sha256 7d1ee8e0...   (1MiB，两次采集一致)
冷状态       plm=0xffffff8f  gfw=0x8b8f/0x3ff/0x10
            WPR2_HI=0  SS0=0x26002014  SS1=0x7
```

**采两次以上，PROM 哈希必须完全一致**——不一致说明显卡状态不稳定，后面别做。

> 踩坑：探针要求内部介质根目录存在 `RTX3090-UNLOCK` 目录。官方 USB 脚本会自动建，手工部署很容易漏，漏了会**静默失败**（不报错也不写文件）。

### 5.3 生成 profile 并通过校验

用采集数据生成一份本机 profile，里面固化上面所有常量。然后跑项目自带的测试套件——这一步不能跳。

我这套跑下来是 **20 项全过**，包括：

- 冷状态读取（9 个寄存器的偏移和期望值）
- PCI 配置一致性、BAR 描述符
- 驱动所有权图（哪些 agent 持有哪个协议）
- 拒绝用例：单次采集、采集互相矛盾、PROM 换了、芯片没验证过、显存没验证过……

只有测试全过，profile 才被认为「有写权限」。

### 5.4 构建两个 EFI

架构是**两级**：

```
包装层 HEADLESS.EFI (42KB)
  ├─ 校验冷状态、读 PROM、释放显示驱动、恢复 PCI 解码
  └─ LoadImage → 子程序 UNLOCK-HEADLESS.EFI (68KB)
                    ├─ 二次校验（BDF、配置、BAR、PROM、冷状态）
                    └─ V67/PLM 提权 → 写 SS0/SS1 → FLR → 交接回包装层
```

包装层最后链式加载 Windows 的 `bootmgfw.efi`，把控制权交回去。

### 5.5 部署与启动项（这里有最大的坑）

**坑 1：Windows 启动管理器不是加载自有 EFI 的通道**

我试过三条路：

| 方式 | 结果 |
|---|---|
| `bcdedit /copy {current}`（osloader 类型） | `0xc000007b`，bootmgr 按 Windows 加载器校验，拒绝执行 |
| `bcdedit /create /application bootsector` | 静默跳过，看起来啥也没发生 |
| **`bcdedit /copy {bootmgr}`** | ✅ 能加载任意 EFI 应用 |

**`{bootmgr}` 的副本才具备「加载任意 EFI」的能力**，这是关键。复制完再改 `device` 和 `path`：

```
bcdedit /copy {bootmgr} /d "GPU Headless UNLOCK - EXPERIMENTAL"
bcdedit /set {新GUID} device partition=F:
bcdedit /set {新GUID} path \EFI\WindowsGPUUnlock\HEADLESS.EFI
```

**坑 2：资产路径**

解锁程序按 `Parent\ASSETS\xxx.bin` 查找，`Parent` 是 `\RTX3090-UNLOCK`，所以正确位置是：

```
F:\RTX3090-UNLOCK\ASSETS\*.bin
```

放成 `F:\ASSETS\` 会找不到，返回 `EFI_NOT_FOUND`。

## 六、两个真正卡住我的根因（最值得看的部分）

前面所有流程都通了，但冷状态检查一直返回 `0xE`、9 个寄存器全读到 0。
排查了整整一晚，方向全错。最后发现是两个低级错误。

### 根因 1：把 `0xE` 当成了 `EFI_NOT_READY`

这是最大的时间黑洞。

```
EFI_NOT_READY  = 0x8000000000000006
EFI_NOT_FOUND  = 0x800000000000000E   ← 一直是这个
```

我一开始按「NOT_READY」理解，于是所有推理都指向**「显卡不是冷启动状态」**：查热启动、查断电时序、查固件驱动抢占、查 BAR 映射……全是错的。

实际含义是「**没找到设备**」。

教训很直接：**遇到 EFI 状态码，先查定义表再推理**。第一步就错，后面每一步都在加深误解。

### 根因 2：包装层编译漏了一个宏

`GuPeekCold()` 匹配设备时用 `GU_BOARD_ID` 和 `GU_BOARD_SUBSYSTEM` 两个常量。这两个值来自 profile 头文件，但——

```c
// machine-profile.h
#if defined(GU_PROFILE_LOCAL)
#include "profile-local.h"        // ← 只有定义了这个宏才会包含
#else
#define GU_BOARD_ID 0x220410deU   // ← 否则回落到默认的 3090
#define GU_BOARD_SUBSYSTEM 0x88701043U
#endif
```

子程序是用构建脚本编的，脚本正确传了 `-HardwareProfile local`。
但**包装层是我手工编译的，漏了 `-DGU_PROFILE_LOCAL`**。

后果：包装层拿着 3090 的身份（`0x220410de`）去匹配这张 3060 Ti（`0x24c910de`），永远匹配不上，`found=0`，返回 `EFI_NOT_FOUND`（`0xE`）。

这就完整解释了「9 个寄存器全 0」——**根本没走到读寄存器那一步**。

修正后一行搞定：

```diff
- clang ... -DGU_FULL_UNLOCK -DGU_AUTOMATIC_BOOT -DGU_HEADLESS_RESEARCH -DGU_SINGLE_RTX_CONSOLE
+ clang ... 同上 + -DGU_PROFILE_LOCAL
```

### 怎么定位出来的

值得说一下方法，因为前面几次尝试都是无效的。

我一开始不停地往包装层里加日志，结果日志要么写不出来，要么写出来全是 0——因为**整个二进制都没匹配到设备**，后面的代码一行没执行。

真正破局的是写了一个 **6KB 的最小只读程序**：只做一件事，枚举 PCI、找到 `24c910de`、读 9 个寄存器、打印到屏幕。

屏幕上打出了完整真值。这就证明了三件事：

1. 硬件可读
2. 那个时刻的环境没问题
3. 问题一定在包装层自己的代码路径里

然后我把包装层的判断逻辑**原样复制**进这个小程序，它返回 `status=0x0`（通过）。于是矛头指向「包装层这个二进制和它不一样」，再顺着差异找到常量宏。

最后一步是把「当前找到几个设备」打到屏幕上——`found=0` 三个字符，直接锁定了问题。

**方法论**：当大程序里什么都看不到时，先把同样的逻辑搬进一个能跑通的最小程序里。能跑通 → 差异在环境或链接；跑不通 → 差异在代码本身。这一步把排查空间从「无限」压到「二者之一」。

## 七、开机自动执行：还有一个坑

解锁是**易失的**，断电就失效，所以每次开机都要重新执行一次。

第一版方案：把解锁项排到固件启动顺序第一位。

```powershell
bcdedit /set {fwbootmgr} displayorder {解锁项} {bootmgr} {其他}
```

设置后验证是通过的。但**下一次开机它又变回去了**：

```
设置后:  {fa8c…} {bootmgr} {d9cc…}
开机后:  {bootmgr} {d9cc…} {fa8c…}   ← 被改回来了
```

原因：**Windows Boot Manager 每次启动都会把固件启动顺序改回自己第一**。这是它的正常行为，你在外面改多少次都会被覆盖。

正确做法是在 **Windows 内部武装下一次启动**，用一次性的 `bootsequence`：

```powershell
bcdedit /set {fwbootmgr} bootsequence {解锁项GUID}
```

然后注册一个登录时触发的计划任务，每次登录都重新武装：

```
开机 → 固件读 bootsequence → 解锁程序 → 解锁 → 链式启动 Windows
     ↑                                                    ↓
     └────────── 登录时任务重新武装 bootsequence ←──────────┘
```

这个闭环实测有效：

```
计划任务 GPUUnlock-ArmNextBoot   最后运行 22:37:37   结果 0
bootsequence                     已指向解锁项（为下一次开机武装好）
AUTO000003                       22:37 自动创建（没按任何键）
SS0=88888888  SS1=00000008       FINAL status=0  attempted=1
```

## 八、收益边界：别抱不切实际的期待

这一点很重要，很多人解锁完会失望。

| 场景 | 收益 | 原因 |
|---|---|---|
| GEMM / 训练 / LoRA / 微调 | **+80% 左右** | 计算密集，直接吃满 |
| SD / 扩散模型推理 | 明显提升 | 同样是计算密集 |
| LLM 预填充（prompt 处理） | **+14% ~ +36%** | 部分受限于其他环节 |
| **LLM 逐 token 生成** | **≈ 0** | 受显存带宽限制 |
| 游戏 | 无 | 走 CUDA 核心 FP32，不碰这条路径 |

我实测了显存带宽：

```
D2D copy (read+write):  487.6 GB/s   （规格 ~448 GB/s，已经跑满）
decode GEMV 4096x11008: 492.9 GB/s 有效带宽
```

所以如果你主要用 llama.cpp 跑 GGUF 量化模型，**解锁基本没感觉**——瓶颈从来不是算力，是带宽。收益只在「一次处理大量 token」的预填充阶段，以及训练、微调、图像生成这些真正吃算力的场景。

## 九、风险与回滚

**风险**

- 修改 GPU 内部寄存器属于非官方操作，可能损坏硬件、失去保修
- 解锁过程会释放显示驱动，屏幕会黑十几秒；如果中途异常，屏幕可能一直黑
- 上游只验证过 5 组「主板 + 显卡」组合，非公卡和不同 BIOS 都算未验证

**兜底**

- `bootsequence` 是一次性的，`BootOrder` 不动
- 开机按 F11 永远能直接选 Windows
- 卡住时长按电源 10 秒关机，再开机进 Windows

**回滚**

```powershell
# 取消自动执行、清除武装、还原启动顺序
.\tools\unlock-manage.ps1 -Disable

# 彻底撤销：删启动项、删分区、空间还给 C 盘
bcdedit /delete {解锁项GUID}
Remove-Partition -DiskNumber 1 -PartitionNumber 4 -Confirm:$false
$p = Get-Partition -DiskNumber 1 -PartitionNumber 3
Resize-Partition -DiskNumber 1 -PartitionNumber 3 -Size ($p.Size + 2GB)
```

安全启动记得自己开回去。

## 十、一句话总结

技术上真正难的**不是**解锁本身——那部分上游已经写好了，而且是「改两个寄存器 + 一次复位」这样简单的东西。

难的是三件事：

1. **判断有没有锁**（用归一化 FLOP/clk/SM，别看绝对值）
2. **让程序在正确的位置、以正确的身份运行**（少一个编译宏就全盘失败）
3. **读懂错误码**（`0xE` 是 NOT_FOUND 不是 NOT_READY，一个误读能让人走一整晚弯路）

至于收益，先想清楚你的瓶颈是不是算力。如果是显存带宽，解锁只是白折腾。
