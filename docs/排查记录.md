## 二、卡点：冷状态检查读回全 0

### 现象

`HLS000000.TXT` 每次都一样：

```
pre-release-cold-check status=0x800000000000000e   ← EFI_NOT_READY
early-cold-chip         status=0x0000000000000000   ← 入口采样也是 0
cold0..cold8            status=0x0000000000000000   ← 9 项全 0
full-unlock-skipped-no-driver-release
```

### 已排除的原因

| 假设 | 验证 | 结果 |
|---|---|---|
| 热启动状态不对 | 断电 3 分钟冷启动 | 排除 |
| 固件驱动抢占时序 | 把 `GuPeekCold` 提到 `efi_main` 入口 | 排除（仍是 0） |
| 硬件不可读 | 同一次冷启动跑探针 | 排除（探针读到真值） |
| 部署了旧版本 | 核对 sha256 + 字符串 | 排除 |
| PciIo 指针变化 | 改成按 bus/dev/fun 重定位 | 已改，未解决 |

### 剩余最可能原因

`GuPeekCold` 里：

```c
if(!Bytes(cfg,expected,sizeof(cfg)))return EFI_NOT_READY;   // PeekConfig
```

或 `ColdRead` 里的 `io->Mem.Read` 返回"成功但值为 0"。而 9 项全 0 且 `ColdRead` 之前的 `cold[]` 未被填充，指向 **`PeekConfig` 提前返回**。

### 一个未解决的调试障碍

我在 `full-release.c` 里加的 `Note()` 阶段日志**始终没有输出**（`cold-stage1-config`、`peekconfig-relocated` 等字符串确认在二进制内，但日志里没有）。这条通道不可靠，导致无法定位到具体是哪一步。

## 三、明天的建议做法（一次开机可定性）

### 不要再用日志文件，改成屏幕输出

写一个**最小 EFI**，只做一件事：

1. 枚举 `PciIo`，找到 `24c910de`
2. 读那 9 个寄存器
3. 用 `ConOut->OutputString` **直接打印到屏幕**
4. 链回 Windows

这样绕开所有日志、钩子、文件系统问题。你拍照给我，一眼就能看出：

- 如果屏幕显示真值 → 问题在 `GuPeekCold` 的校验逻辑（可修）
- 如果屏幕也是 0 → 包装层的 PciIo 用法与探针有本质差异（可对比 `probe.c` 与 `full-release.c` 的 `ProbeBar`/`ColdRead`）

### 代码差异线索

探针 `probe.c:311-340` 与 `full-release.c` 的 `GuPeekCold` 获取 `io` 的方式**几乎相同**（都是 `HandleProtocol` + `PciGuid`），但：

- 探针先做 `probe-inventory` 统计所有显示设备
- 探针的 `ProbeBar` 额外检查 `GetBarAttributes` 的 `AddrLen==0x1000000`
- `GuPeekCold` 在 `ColdRead` 前额外做了**两次** `PeekConfig` 和一次 `PeekBar`

怀疑点：`PeekConfig` 第二次比对（`cfg` 与 `expected` 全 128 字节相等）可能因为固件在两次读之间改了某个配置字而失败。

## 五、值得记住的两个结论

1. **Windows 启动管理器不是加载自有 EFI 的通道**——两条常规路径（`osloader`/`bootsector`）都会被拒。必须写固件 `Boot####`。
2. **内部介质路线缺少 `RTX3090-UNLOCK` 目录会导致静默失败**——官方 `prepare_usb.py` 会预建，手工部署必须自己补。
